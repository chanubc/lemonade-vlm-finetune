## 0. 이 문서의 목적
이 프로젝트의 **PoC 단계**를 Claude Code가 이어받아 실행하기 위한 핸드오프.

- 관련 스크립트: `scripts/step0_baseline.py`, `step0c_cooking_baseline.py`,
  `collect_incident_frames.py`, `step1_crop_label_holdout.py`. 결과: `results/step0*_*.md/json`.

## 1. 프로젝트 한 줄
합성/시뮬 데이터로 파인튜닝한 소형 VLM이 **조리 환경의 돌발상황(화재·수증기·기름넘침)을 인식**하고, 그 결과로 로봇의 다음 행동(정지/계속/열원차단)을 트리거하는 시스템. 핵심 기여는 **인식(VLM)**, 반응은 규칙 기반 트리거.

## 2. 문제의식
- 조리 재난·돌발 데이터는 안전·윤리상 실제 수집이 불가능 (자율주행이 실제 사고를 못 내 시뮬로 코너케이스를 만드는 것과 동일 구조).
- 기존 rule-based는 미지의 돌발상황에 대처 불가 → 그래서 학습 기반 인식이 필요.
- 정상 조리는 rule-based로도 되지만, **돌발상황 판단은 안 됨** → 여기가 AI가 필요한 지점.

## 3. 최종 방향 (확정 — STEP 0/0-C 근거 반영)
- **태스크 = "정상 조리 vs 위험" 분류 (오탐 억제 + 발연/화재 단계 인식).** 클래스 = normal / smoke(발연) / fire.
  단순 "화재 유무"가 아니다 (기본 모델이 이미 함). 핵심 가치는 **정상 김·튀김을 위험으로 오판하지 않기 + 발연 단계 구분**.
- 학습 데이터 = **하이브리드** (실프레임 위 불꽃/발연 합성 우선 + 실화재 공개셋 + Babylon 렌더 보조). 시뮬 단독 학습 금지.
- 학습법 = **VLM(Qwen2.5-VL-3B 우선) + QLoRA + VQA형 SFT (지도학습 분류)**.
- 검증 = **조리 도메인 실 홀드아웃으로 F1/오탐률** (학습 미사용). 야외 D-Fire는 도메인 불일치라 평가 부적합.
- 데모 = **Babylon.js 웹3D** (가상 CCTV 캡처 → VLM → 로봇 반응 실시간 루프).
- 도구 결정: 데모/시뮬은 **Babylon.js**. 단, **불 픽셀 생성의 주력은 실프레임 합성**이고 Babylon은 데모 루프·대조군(시뮬 팔)로. Isaac Sim 제외.

## 4. 확정된 기술 스택
- 모델: Qwen2.5-VL-3B (대안: Kanana-1.5-v-3b) — STEP 2에서 실측 후 확정
- 학습: PyTorch, QLoRA (4bit + LoRA 어댑터), PEFT
- 서빙: vLLM (데모 단계)
- 시뮬/데모: Babylon.js
- GPU: 1대 확보됨 (렌탈)
- 합성: Python + OpenCV/PIL

## 5. 핵심 리스크 (반드시 먼저 해소)
**"기존 VLM이 이미 화재를 인식할 수 있다"** → 그러면 "단순 화재감지"는 프로젝트로 약함.
- 그래서 STEP 0에서 **기본 VLM의 화재 F1을 먼저 측정**한다.
- baseline F1이 높으면(예: 0.85+) → 태스크를 어렵게 전환:
  - (A) "수증기(정상) vs 화재 연기(위험)" 구분, "과열/개입 타이밍(transition point)" 판단 등 **조리 맥락이 필요한 어려운 태스크**로.
  - (B) "**온디바이스 소형 3B 모델**로 대형 모델급 인식을 실시간·로컬로" 라는 정당화(distillation 스토리).
- baseline F1이 낮으면 → 단순 화재감지도 파인튜닝 가치 있음, 그대로 진행.

## 6. 실행 순서 (이 순서대로)

### STEP 0 — 기본 VLM 베이스라인 측정 ✅ 완료
**결과:** D-Fire(야외)로 F1 **0.819**, 재현율 0.97, 오탐 40%. → 단순 화재감지 약함.
스크립트 `scripts/step0_prepare_dfire.py` + `step0_baseline.py`, 결과 `results/step0_baseline.md`.

### STEP 0-C — 조리 도메인 재측정 ✅ 완료 (방향 확정)
**결과:** 실화재 재현율 100%인데 정상 조리 오탐 15%(랜덤)/44%(hard), 발연 100% 오답.
→ 태스크를 "정상 vs 위험(발연/화재 단계)"으로 확정. 스크립트 `step0c_cooking_baseline.py`, 결과 `results/step0c_cooking.md`.

### STEP 1 — 데이터 소스 확보
1. **실화재셋**: D-Fire에서 학습용 200~300장 + **홀드아웃 100~150장(학습에 절대 미사용, 별도 폴더로 격리)**.
2. **실프레임(정상 베이스)**: 사용자 제공 튀김 영상(구글드라이브)에서 ffmpeg로 프레임 추출 → 조리기 ROI 크롭. (영상은 사용자가 제공; 접근 안 되면 사용자에게 요청)
3. **합성 재료**: 실화재셋/BoWFire에서 불꽃 컷아웃 확보(마스크 있으면 그대로 alpha).

### STEP 2 — 합성 파이프라인 (Python/OpenCV) 🔨 착수
실 조리 프레임(LEMONADE) **위에** 불꽃/발연을 합성한다 (배경=실도메인 유지가 핵심). 웹3D 위에 합성 아님.
- **불꽃 컷아웃 소스 = NIST 실화재 프레임**(어두운 배경 → 휘도+온기(R−B) 마스크로 alpha 추출; 흰 격자선 배제).
- 조리기 위치(오버헤드 중앙)에 랜덤 스케일·위치·밝기로 합성 (screen/additive), 발연=반투명 회색 plume 오버레이.
- 도메인 랜덤화 증강: 조명·노이즈·블러·색온도 랜덤 (전이 위해 필수).
- 3클래스 자동 라벨: 아무것도 안 얹으면 normal, plume=smoke, 불꽃=fire.
- **누수 주의:** 학습 배경으로 쓰는 LEMONADE 세그먼트는 홀드아웃 정상과 겹치지 않게 분리(향후 세그먼트 단위 split 고정).
**산출물:** `data/synth/{normal,smoke,fire}/*.jpg` + `labels.jsonl`. 스크립트 `scripts/step2_composite.py`.

### STEP 3 — Babylon.js 렌더 데이터 (병렬 가능)
- 기존 HTML 조리 시뮬레이터 자산 재활용 → Babylon으로 튀김기 씬 + **불 파티클(fire 토글)**.
- 고정 카메라(CCTV 시점) 1대. 불 크기·위치·조명·각도 랜덤화.
- 자동 캡처로 fire/normal 각 200장(다양성 확보).
**산출물:** `data/babylon/{fire,normal}/*.jpg`
**주의:** 양보다 다양성. 똑같은 장면 200장은 무의미.

### STEP 4 — 3-way 학습 + 비교 (핵심 실험)
학습법(QLoRA + VQA SFT)은 고정, **학습 데이터만 3가지로** 바꿔서 같은 홀드아웃으로 F1 비교.
- A. Babylon 렌더만 학습 → F1
- B. 실프레임 합성만 학습 → F1
- C. 하이브리드(A+B+실화재 일부) 학습 → F1
- 평가셋: **STEP 1의 실화재 홀드아웃 100%** (셋 다 동일, 합성 0%)
**산출물:** `results/step4_3way_f1.json` (표: baseline / A / B / C)
**해석:** A가 높으면 "웹3D 전이 성립"(강한 결과), A 낮고 C 높으면 "하이브리드가 답"(문헌 일치). 어느 쪽이든 결과.

### STEP 5 — 데모 (실험 통과 후)
- Babylon 가상 CCTV 화면 캡처 → 서빙된 파인튜닝 VLM 호출(1~3초 주기) → 판단 → 로봇 반응(정지/경광등).
- 인식은 실제 모델 output으로 (시나리오 재생 금지 — 그러면 프로젝트 부정).
- 추가 하이라이트: 공개 실화재 **동영상**을 프레임 단위로 흘려넣어 "실화재 실시간 인식" 시연.

## 7. 평가/데이터 규칙 (절대 위반 금지)
- **평가는 항상 학습에 안 쓴 실데이터로.** 합성/Babylon으로 학습하고 합성/Babylon으로 평가 = 순환구조, 금지.
- 홀드아웃은 물리적으로 별도 폴더 격리, 학습 스크립트가 절대 못 읽게.
- 클래스 균형 유지(fire/normal 장수 비슷).
- 학습셋 믹스 시작 비율(권장): 실사진 30% / 합성 60% / Babylon 10%. 검증셋은 실사진 100%.

## 8. 데이터 규모 (참고)
- PoC: 클래스당 학습 150~200장 + 홀드아웃 100~150장.
- 본학습: 클래스당 500~1000장 + 홀드아웃 200~300장.
- Babylon 렌더는 무제한 생성 가능 → 양보다 다양성·홀드아웃 확보가 관건.

## 9. 클래스 (STEP 0-C 반영, 3단계로 확정)
1. **normal (정상)** — 김·수증기·튀김·볶음·주황음식·달군 팬. LEMONADE 등 실조리 프레임 풍부. **오탐 억제의 핵심.**
2. **smoke (발연/위험 연기)** — 정상 김이 아니라 기름 발연 등 위험 조짐. 기본 모델이 못 구분(100% fire 오답)하는 지점.
3. **fire (화재)** — 실제 불꽃. 공개셋(NIST FCD 등) 있음.
- (후순위) 기름넘침 — 실데이터 거의 없음, 합성 보조. 사람접근 — 데모 전용, 인식 검증 대상 아님.

## 10. 레퍼런스 (근거)
- FireFly (arXiv:2308.03164) — 게임엔진 합성 화재 → 실화재 전이 성공(mAP +8.57%). 핵심 선례.
- SYN-FIRE (Sci. Reports 2025, nature.com/articles/s41598-025-01571-5) — Omniverse 실내화재 합성, 합성/실 혼합 효과.
- Sim-to-Real Fruit Detection w/ Isaac Sim (arXiv:2603.28670) — 하이브리드 > 합성단독, 실데이터 근접.
- Tobin et al. 2017 (arXiv:1703.06907) — Domain Randomization.
- AgentSGEN (arXiv:2505.13466) — 위험사건 수집 불가 → 합성 필수 전제.
